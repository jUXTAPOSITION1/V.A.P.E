## ERC-8183 / ACP Contract Cross-Reference

### What is ERC-8183?
ERC-8183 is a proposed Ethereum standard (co-developed by **Virtuals Protocol** and the **Ethereum Foundation's dAI team**, announced March 9, 2026) for **trustless AI agent commerce**. It introduces a "Job" primitive with three participants (Client, Provider, Evaluator) and programmable escrow. It is designed to work alongside:
- **ERC-8004** — agent identity and reputation registry
- **x402** — HTTP-native micropayments

Before ERC-8183, Virtuals' internal tracker recorded **$3M+ in agent-to-agent transactions across 3,400+ agents with NO escrow, delivery verification, or recovery mechanism**.

### Threat Assessment for ERC-8183 / ACP Contracts

| Risk Vector | Severity | Detail |
|-------------|----------|--------|
| **Evaluator Compromise** | 🔴 CRITICAL | The Evaluator is the sole authority to approve/reject a Job. A compromised evaluator (AI agent, multisig, or ZK contract) could release escrow fraudulently. Mirrors the Drift Security Council compromise pattern. |
| **Escrow Drain via Hook Exploits** | 🔴 CRITICAL | ERC-8183's modular "Hook" extensibility for custom logic creates a broad attack surface. Malicious or poorly audited hooks could redirect escrowed funds — analogous to the Aperture Finance arbitrary-call vulnerability ($3.67M). |
| **Single-Point-of-Failure in Verification** | 🟠 HIGH | The Kelp DAO exploit demonstrated that single-DVN (Decentralized Verifier Network) configurations are catastrophic. ERC-8183's Evaluator role, if implemented as a single entity rather than a multisig/committee, replicates this failure mode. |
| **Social Engineering of Agent Operators** | 🟠 HIGH | The Drift exploit showed that multi-month social engineering campaigns can compromise even Security Council members. AI agent operators are potentially softer targets than institutional signers. |
| **Batch Deployment Vulnerabilities** | 🟡 MEDIUM | On Base chain specifically, batch deployments of ERC-8183 contracts can propagate misconfigurations across multiple contracts simultaneously. OWASP 2026 SC Top 10 lists access control as #1 risk. |
| **Pre-Standard Exploitation Window** | 🟡 MEDIUM | ERC-8183 is still in draft/EIP discussion. Implementations deployed before finalization may contain spec ambiguities exploitable by attackers. $3M+ in transactions already occurred without escrow protections. |
| **Reentrancy in Job Lifecycle** | 🟡 MEDIUM | The Job state machine (Open → Funded → Submitted → Completed/Rejected) involves multiple contract interactions. Reentrancy remains a persistent 2026 vulnerability class per IGNA analysis. |

Closed-source contracts made analysis difficult. This is the **only confirmed major 2026 exploit directly affecting Base chain**.

- **ERC-8183 on Base**: As an EVM-compatible L2, Base will host ERC-8183 contracts. The same batch deployment patterns that caused Aperture's cross-chain exploit apply to ERC-8183 Job contracts deployed in bulk on Base.
- **Bridge Dependency**: Base relies on bridges for cross-chain liquidity. The $328.6M in 2026 bridge hacks (8 incidents) is directly relevant — any ACP/ERC-8183 contract interacting with cross-chain bridges inherits these risks.

## Actionable Recommendations

1. **Mandate multisig Evaluator configurations** for all ERC-8183 / ACP Jobs above $10K. Single-entity Evaluators replicate the single-DVN failure that destroyed Kelp DAO.
2. **Audit all Hook implementations** before deployment. Treat Hooks as privileged code equivalent to admin functions.
3. **Implement transaction simulation** (e.g., GateSigner-style pre-execution evaluation) for all ACP contract interactions to detect anomalous behavior before on-chain execution.
4. **Enforce multi-DVN bridge configurations** for any ACP jobs involving cross-chain asset movement. Single-DVN is a known catastrophic failure mode.
5. **Deploy time-locks on escrow release** — even a 1-hour delay enables intervention in active exploits.
6. **Revoke unnecessary token approvals** — Aperture-style arbitrary-call vulnerabilities exploit broad ERC20/NFT approvals.
7. **Verify all agent operator identities** — implement KYC-equivalent verification for high-value ACP participants to counter DPRK-style long-con social engineering.
