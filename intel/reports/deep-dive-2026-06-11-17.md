## EXECUTIVE SUMMARY

EIP-7702, activated via the Ethereum Pectra hard fork in May 2025, enables Externally Owned Accounts (EOAs) to temporarily delegate execution to smart contract code. While this unlocks powerful account abstraction features — batch transactions, gas sponsorship, sub-keys — it introduces a fundamentally new attack surface that the DeFi ecosystem is struggling to adapt to. **At least three distinct exploits have been documented since October 2025, with losses totaling $672K+, and the attack pattern is accelerating.**

The critical insight: EIP-7702 delegation is not a simple "approve and forget" — it is closer to **installing software on your wallet**. Every delegation point introduces smart contract risk to what was previously a key-management-only security model. For the ACP/ERC-8183 agent ecosystem on Base, where agents manage escrowed USDC and interact with delegation-enabled smart accounts, this threat is structurally significant and currently underappreciated.

## ANALYSIS

### 1. What EIP-7702 Does and Why It Matters

EIP-7702 introduces a new transaction type that allows EOAs to set a "delegation designator" — a pointer (`0xef0100 || address`) to an on-chain smart contract. Once set, any `CALL` to the EOA executes the delegate contract's code instead, while the EOA retains its own storage and the private key retains full control.

**Key capabilities unlocked:**
- Batch operations (multiple actions in one transaction)
- Paymaster gas sponsorship (users don't need ETH for gas)
- Sub-keys with limited scope and spending limits
- Recovery mechanisms for lost private keys
- Account abstraction without migrating to a new address

**Why this creates risk:** An EOA's security model is simple — protect the private key. With EIP-7702 delegation, the security model becomes: protect the private key **AND** ensure the delegated contract has no vulnerabilities. This is a qualitative expansion of the attack surface.

### 2. Documented Exploits — A Growing Timeline

#### Incident 1: BNB Chain Delegation Contract Exploit (October 3, 2025)
- **Loss:** $336,000 USDT
- **Chain:** BNB Chain
- **Mechanism:** Victim's EOA delegated to a contract with an unprotected `pancakeV3SwapCallback()` function — no access control, anyone could call it. Attacker invoked the callback and drained USDT.
- **Root Cause:** "Blind trust" delegation — user delegated without verifying the contract's access controls.
- **Key Distinction:** Unlike phishing, the private key was not compromised. The exploit leveraged legitimate delegation functionality with insecure implementation.

#### Incident 2: IPOR Fusion PlasmaVault Exploit (January 6, 2026)
- **Loss:** $336,000 USDC
- **Chain:** Arbitrum
- **Mechanism:** Attacker exploited the intersection of a legacy vault's missing validation in the "fuse" logic AND EIP-7702 delegation. The project team's EOA controlled admin functions through an EIP-7702 delegate contract. The attacker used a malicious "fuse" contract configuration to redirect all vault funds during a withdrawal call.
- **Root Cause:** Two independent factors converging — a 490-day-old vault lacking strict validation safeguards (which newer vaults had) + EIP-7702 delegation enabling the attack path.
- **Recovery:** IPOR DAO fully reimbursed users from treasury (loss was <1% of total Fusion AUM).
- **Key Lesson:** "Upgrade friction" — new Ethereum features can unintentionally create backdoors in unpatched legacy contracts.

#### Incident 3: QNT Reserve Pool Drain (April 29, 2026)
- **Loss:** 1,988.5 QNT (~54.93 ETH)
- **Chain:** Ethereum Mainnet
- **Mechanism:** The QNT reserve pool's admin EOA delegated to a `BatchExecutor` contract, which mistakenly authorized `BatchCall` as a caller. The `BatchCall.batch()` function had no permission checks, allowing anyone to execute unauthorized batch transactions and drain the pool.
- **Root Cause:** Misconfigured delegation chain — EOA → BatchExecutor → BatchCall — with missing access control at the terminal node.
- **Key Lesson:** Delegation chains amplify risk. Each hop is an access control decision, and a single missing check at any point in the chain exposes the entire account.

#### Phishing-Driven Delegation Attacks (April 2025 — ongoing)
- **Estimated Loss:** $5M+ in April 2025 alone (Coin Republic reporting)
- **Mechanism:** Social engineering attacks tricking users into signing EIP-7702 authorization tuples, delegating their accounts to attacker-controlled contracts.
- **Scale:** The Bybit hack ($1.4B, February 2025) demonstrated the consequences of inadvertently delegating control to a malicious actor via compromised proxy infrastructure.
- **Key Lesson:** The new "authorization tuple signature" is poorly understood by users. A single malicious delegation is all that's needed.

## APPENDIX: Technical Reference — EIP-7702 Attack Vectors (from Nethermind)

### A1. Missing Access Control (Most Exploited Pattern)
```
// VULNERABLE — anyone can call this on the delegated EOA
contract VulnerableContract {
    function doSomething(bytes memory _data, address _to, uint _value) public payable {
        (bool success, ) = _to.call{value: _value}(_data);
        require(success);
    }
}
```
**Mitigation:** All external functions must enforce `require(msg.sender == address(this))` or use role-based access control.

### A2. Front-Running Initialization
When a user delegates in one transaction and calls `initialize()` in a second transaction, an attacker can frontrun the `initialize()` call and take control of the account.
**Mitigation:** Delegate and initialize in the same atomic transaction.

### A3. Storage Collision on Redelegation
Delegating from ContractA (storage slot 0: `bool`) to ContractB (storage slot 0: `uint256`) causes the uint to be interpreted as a bool.
**Mitigation:** Use storage namespaces, EIP-7201 namespaced storage, or stateless contract patterns designed for EIP-7702.

### A4. Pre-7702 Contract Incompatibility
Any smart contract wallet built before EIP-7702 lacks initialization protection and storage collision safeguards. Delegating to these is "the most dangerous action" (Fireblocks).
**Mitigation:** Only delegate to contracts specifically built for EIP-7702 with stateless/protected initialization.
