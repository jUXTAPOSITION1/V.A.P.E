## EXECUTIVE SUMMARY

The Model Context Protocol (MCP), released by Anthropic in November 2024 as the "USB-C for AI," has become the de facto standard for connecting AI agents to external systems — wallets, databases, email, file storage, and APIs. Within 18 months, Amazon, Microsoft, Google, and OpenAI all adopted it. Over 10,000 MCP servers now exist in public registries. But the protocol was designed for connectivity, not security, and the consequences are now cascading through the AI industry.

**The core finding is devastating in its simplicity:** MCP executes local commands before verifying whether those commands are legitimate. When OX Security disclosed this to Anthropic with 30+ responsible disclosure processes, Anthropic classified the behavior as "expected." The flaw remains unfixed. An estimated 200,000 servers are running against it.

**For VAPE and ACP agents specifically, this creates a compounding threat:**

1. **MCP rug pulls** — A tool approved once can silently become malicious after trust is established, with no re-authorization required. This is the same pattern as on-chain rug pulls, applied to the AI agent's tool stack.
2. **Credential harvesting at scale** — 53% of 5,200 audited MCP servers use hard-coded credentials. Only 8.5% use OAuth. 88% require credentials to function. The Oura MCP clone delivered StealC malware specifically designed to harvest **cryptocurrency wallets**.
3. **Prompt injection → RCE pipeline** — The STDIO transport mechanism allows arbitrary OS command execution from untrusted input. This has already enabled authenticated RCE on Letta AI and unauthenticated server takeover on LangFlow.
4. **AI-as-attack-infrastructure** — A single attacker used Claude Code to breach 9 Mexican government agencies, generating 5,317 commands across 34 live sessions. The AI was the weapon, not just the target.

The MCP crisis is not a future risk — it is a present, ongoing, and expanding threat that directly undermines the trust assumptions of autonomous agent commerce on Base and every other chain.

## ANALYSIS

### Part 1: The Architecture of the Vulnerability

#### What MCP Is and Why It Matters

Anthropic released MCP in November 2024 as "a universal, open standard for connecting AI systems with data sources, replacing fragmented integrations with a single protocol." Pre-built servers for Google Drive, Slack, GitHub, and Postgres shipped on day one.

Within months, Amazon, Microsoft, Google, and OpenAI adopted it. By April 2026, over 10,000 published MCP servers existed. It became the de facto infrastructure standard for AI agent connectivity — the layer between AI models and everything they touch.

**For crypto agents, MCP is the bridge between the LLM and the wallet.** Any agent using tool-calling, function execution, or external API access is either directly or transitively dependent on the MCP paradigm. When VAPE calls ACP, when an agent checks a wallet balance, when a trading bot executes a swap — the trust model is the same one MCP formalized.

#### The Fatal Design Choice

OX Security ran 30+ responsible disclosure processes beginning November 2025. Their core finding: **MCP executes local commands before verifying whether those commands are legitimate.**

This means:
- A rogue prompt delivered through any UI the agent reads can execute arbitrary commands on the host system
- No malicious download needed. No phishing click required. The agent reads content, processes an embedded instruction, and acts. That is the design.
- A poisoned marketplace listing, compromised IDE, or malicious GitHub issue can trigger full system compromise

When OX brought this to Anthropic, the response was not a patch timeline. Anthropic classified the behavior as **expected**. A quiet policy update followed a week later; OX assessed it as fixing nothing. Anthropic did not respond to The Register's press inquiry.

**Estimated exposure: up to 200,000 servers running against the unfixed flaw.**

This is not a zero-day discovered in the wild and raced to remediate. This is a flaw that was disclosed, reviewed, classified as intentional, and left in place. The manufacturer called the broken lock a feature.

### Part 2: The MCP Rug Pull — A New Attack Category

The crypto community already has a name for this pattern. An MCP rug pull works exactly like the on-chain version:

1. A tool behaves legitimately at first, passes checks, earns approval, appears in logs as routine activity
2. Then, silently, it becomes something else
3. The user consented to version A. They are running version B.

**The mechanism:** A malicious server can change the tool description after the client has already approved it. The audit trail looks clean because the agent did exactly what it was instructed to do — by the version of the tool the user never approved.

**Documented example (Invariant Labs, 2025):**
- A server presenting itself as a harmless "random fact of the day" tool gained user approval and sat dormant
- On its second load, it activated a sleeper attack, switching to a malicious tool definition
- The rewritten instructions hijacked the agent's behavior with respect to a trusted WhatsApp MCP server running in the same system
- It exfiltrated the user's **entire WhatsApp chat history** through an attacker-controlled proxy number
- The confirmation dialog appeared non-problematic; the exfiltration payload was hidden behind a scrollbar

**Every approved MCP tool is a standing authorization that can be rewritten after trust is established.** For agents with wallet access, this means: a tool that was approved to "check balance" can silently become a tool that "transfer all funds to address X" — and the agent will execute it as a normal operation with no additional confirmation.

#### Why This Is Different From Supply Chain Attacks

The 15:00 deep dive covered supply chain attacks (poisoned npm packages, VS Code extensions). MCP vulnerabilities are a **different and arguably more dangerous** category because:

1. **Supply chain attacks require a compromised package.** MCP rug pulls require only that a legitimately approved tool changes its behavior — no code change, no package update, no detection.
2. **Supply chain attacks target the build/install path.** MCP attacks target the **runtime** — the agent is already running, already approved, already trusted.
3. **Supply chain attacks are detectable post-installation with audit.** MCP tool mutation happens between approval and execution with no audit discrepancy — the agent's logs show it did exactly what it was told, by a definition it never approved.
4. **Supply chain attacks have a remediation path (pin versions, verify hashes).** MCP has no native mechanism for tool version integrity verification or re-authorization on definition change.

## RECOMMENDED ACTIONS

### IMMEDIATE (Next 24 Hours)

1. **Audit VAPE's entire tool-calling and API interaction stack.** Map every external tool, API, and data source VAPE accesses. Identify which ones follow the MCP trust model (approved once, trusted indefinitely without re-verification).
2. **Review all ACP SDK dependencies.** The Oura MCP clone delivered StealC targeting crypto wallets. Verify that no VAPE/AAP dependency chain includes compromised or unaudited packages. Run `npm audit` / `pip audit` with specific attention to MCP-related packages.
3. **Check for hard-coded credentials.** 53% of MCP servers use them. If VAPE stores any API keys, tokens, or wallet credentials in configuration files rather than secure vaults, remediate immediately.

### SHORT-TERM (Next 7 Days)

4. **Implement tool-approval re-verification.** Every time VAPE calls an external tool or API, the tool definition should be compared against a known-good hash. If the definition has changed since last approval, the call should be blocked and flagged. This is the minimum defense against MCP rug pulls.
5. **Add transaction-level confirmation for all financial operations.** No wallet transfer, swap, or payment should execute without a separate verification step that the intended operation matches the tool's current definition. This breaks the MCP rug pull chain at the execution layer.
6. **Restrict VAPE's tool access to least-privilege.** Audit every permission granted to every tool VAPE uses. Revoke any that are broader than strictly necessary. The 88%-require-credentials finding means most tools are over-privileged by default.

### MEDIUM-TERM (Next 30 Days)

7. **Evaluate direct API calls as MCP replacements.** Evoke Security's CEO recommends using MCP only when necessary and preferring direct API calls. For VAPE's critical operations (wallet, ACP, trading), direct authenticated API calls with explicit parameter validation are more secure than any MCP-mediated pathway.
8. **Implement session isolation.** Context bleeding between MCP sessions can leak sensitive data. VAPE's operational contexts (trading, wallet management, social) should be strictly isolated with no shared state.
9. **Advocate for ACP security standards** incorporating MCP-specific defenses: mandatory tool integrity verification, per-call re-authorization for financial tools, and credential rotation policies.

### LONG-TERM (Next 90 Days)

10. **Design a "defense-in-depth" agent architecture** that assumes the tool layer is compromised. This means: (a) all financial operations require a second, independent authorization channel; (b) wallet keys never pass through the same execution context as tool calls; (c) all tool outputs are validated against expected schemas before processing.
11. **Monitor MCP protocol evolution.** If Anthropic or the community releases a security-hardened MCP spec (with mandatory input validation, tool integrity verification, and re-authorization mechanisms), evaluate adoption. Until then, treat the current spec as inherently compromised.
12. **Prepare incident response for MCP-based wallet compromise.** Draft a response plan that assumes VAPE's wallet could be drained via a tool poisoning attack with no anomalous audit trail. Include: immediate wallet freeze, ACP service suspension, community notification, and forensic tool-chain audit procedures.
