## Findings

### [HIGH] Owner can burn any holder's tokens (burnFrom)
- `burnFrom(address user, uint256 amount)` is `onlyOwner` with **no consent check**
- Owner can arbitrarily reduce any holder's balance to zero
- Internal `_burn()` does not emit Transfer event — only `burnFrom()` emits `Transfer(address(0))`
- **Impact:** Centralized rug risk — owner can wipe any holder

### [MEDIUM] Owner can change maxTx at any time (updateMaxTx)
- `updateMaxTx(uint256 _maxTx)` is `onlyOwner`
- Can set to 0 (blocking all non-excluded transfers) or 100 (removing limit entirely)
- No timelock or governance on parameter changes
- **Impact:** Owner can throttle or放开 trading at will

### [MEDIUM] Owner can exclude any address from maxTx (excludeFromMaxTx)
- No `includeFromMaxTx` — once excluded, no way back
- No limit on number of excluded addresses
- **Impact:** Owner can whitelist preferred wallets for preferential trading

### [LOW] Internal _burn() does not emit Transfer event
- `_burn()` subtracts balance but only `burnFrom()` emits Transfer to `address(0)`
- If `_burn` is ever called independently, Transfer event is missing (ERC-20 spec violation)
- Currently only `burnFrom` uses `_burn`, so low practical impact

### [INFO] Positive: No mint function — fixed supply
- Total supply set at construction, no way to increase
- This is positive for holders

## Overall Verdict

**⚠️ CAUTION** — Risk Score: 55/100

Centralized owner controls (`burnFrom`, `updateMaxTx`, `excludeFromMaxTx`) pose meaningful risk.  
If owner key is compromised or acts maliciously, holders can be burned or trading restricted.

### Recommendations
1. **Renounce ownership** or add timelock + governance for admin functions
2. **burnFrom** should require user consent (approve pattern) or be removed
3. **updateMaxTx** should have bounds (min/max) and timelock
4. **excludeFromMaxTx** should have a corresponding `includeFromMaxTx`
5. Consider migrating to a more decentralized token standard
